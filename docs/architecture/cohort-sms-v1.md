# Cohort SMS V1 rollout checkpoint

## Status and boundaries

The repository contains the cohort-generic SMS data model, optional Ascenso onboarding phone/consent fields, web meeting check-ins, a Twilio adapter, an inbound webhook, and a protected sender endpoint. This work has not deployed those changes, applied either SMS migration to a hosted database, configured Twilio credentials, or enabled a cohort. It has not inspected those hosted settings. No SMS schedule has been added to `vercel.json`.

`SMS_FEATURE_ENABLED` is absent or false by default. Every `cohorts.sms_enabled` value defaults to false. Both switches must be on for the member SMS preferences, check-ins, and sender to operate. Ascenso can collect an optional phone and separate unchecked consent during application intake while the switches remain off. The current web surveys, email digest, and meeting-log behavior remain separate and unchanged.

## Data path

- Consent belongs to a person within a cohort. The intake route normalizes the US number and records the exact disclosure, version, and server timestamp in `cohort_applications.answers`. Approval copies a missing contact into `cohort_sms_contacts` without overwriting a later member preference. Phone entry alone never authorizes a send.
- `meeting_checkins` is the one channel-neutral answer record for both the authenticated web form and SMS. Each row identifies the cohort, pair, booked session, and member. A check-in answer does not assert attendance or create a `meeting_logs` row. Existing mid-year/end-year `surveys` and `survey_responses` keep their current meaning.
- The sender only considers scheduled sessions 18–30 hours ahead for reminders and sessions 1–25 hours past for check-in prompts. These bounded windows prevent a new cohort enablement from backfilling old meetings. A unique outbox intent allows one reminder and one question per session/contact. A database claim and immediate eligibility recheck precede each provider call. Definite rejection and uncertain acceptance are retained; uncertain sends require manual review and are never automatically resent.
- A Twilio webhook verifies the signature, Account SID, Messaging Service SID, and fixed receiving number. Its inbound parser needs no outbound API key or enabled send switch, so STOP still works during a send outage. The database deduplicates `MessageSid` and records STOP/START/HELP before attempting reply matching. A check-in reply requires its unique 12-character code plus the exact From/To pair, an accepted unexpired prompt, and current member/meeting context. A reply without a unique eligible match is not attributed. Unmatched message bodies are not stored. STOP suppresses the phone across cohorts; START only removes the provider-level block, so a new AP MED consent is still required.

## Setup before a test-number pilot

1. Review and apply `supabase/migrations/20260926201229_sms_foundation.sql`, then `supabase/migrations/20260927023120_sms_atomic_processing.sql`, before deploying dependent code. These are additive but create tables, triggers, and service-role RPCs, so arrange the normal backup and migration review. Do not replay the production baseline. No repository snapshot proves which migrations are already applied to a hosted database.
2. Publish and review AP MED privacy and terms pages for the SMS use case. Create a Twilio Messaging Service with **one fixed two-way US sender** in its pool, configure Advanced Opt-Out, and complete the appropriate US A2P 10DLC Brand/Campaign approval before sending. Keep the onboarding checkbox/disclosure and consent-record evidence available for registration. Configure the inbound **POST webhook on the Messaging Service**, not only the sender number, so signed requests include its Service SID. Use the canonical AP MED hostname for the webhook even if Ascenso has its own public site.
3. Configure server-only `TWILIO_ACCOUNT_SID`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET`, `TWILIO_AUTH_TOKEN`, `TWILIO_MESSAGING_SERVICE_SID`, `TWILIO_FROM_PHONE_E164`, and `TWILIO_INBOUND_WEBHOOK_URL`. Set the last variable to the exact public `https://.../api/webhooks/twilio/sms` URL **without** a fragment. The auth token verifies inbound signatures; the API key sends outbound messages. Never expose these through `NEXT_PUBLIC_` variables.
4. In Twilio, configure the same inbound URL as a POST webhook. For transient failures, the connection override `#rc=2&rp=ct,rt,5xx` is a candidate on the Twilio-configured URL; Twilio excludes that fragment from signature calculation, so keep it out of `TWILIO_INBOUND_WEBHOOK_URL`. Verify this configuration with signed test webhooks and duplicate delivery. A 5xx from the app requests retry; receipt deduplication makes it safe to process again.
5. Keep the existing `CRON_SECRET` for `/api/cron/sms`. The route is implemented but deliberately absent from `vercel.json`: the current repository has only a daily 13:00 UTC email digest, and the hosted plan is unverified. The 12-hour reminder window requires a scheduler at least every 12 hours; an hourly schedule gives more headroom. Check the actual hosting plan and schedule support before registering a cron or promising reminder timing.
6. In a nonproduction environment, test real-number delivery and inbound messages, duplicate and late webhooks, STOP, START followed by fresh web consent, phone changes, canceled meetings, overlapping cohorts, web answers before SMS replies, provider timeouts, and stale sending reconciliation. Inspect `needs_review` rows against Twilio before resolving them. Only then request authorization to enable the Ascenso cohort in production.

## Known limits

- No handset ownership check is performed. Shared, mistyped, or reassigned numbers may receive a short prompt; keep detailed program information in the authenticated web dashboard.
- Provider acceptance is not handset delivery. V1 does not consume Twilio delivery-status callbacks; review provider message logs when investigating a missing text or a `needs_review` attempt.
- A STOP can race with an already claimed provider call. The sender rechecks eligibility immediately before calling Twilio, and Twilio's own opt-out enforcement is the final backstop; an external send cannot be atomic with a database update.
- The sender uses bounded per-run limits. If the pilot exceeds those limits or a scheduler is down beyond the due window, SMS may be skipped rather than sent late. The web check-in remains available. Operators should inspect stale `sms_outbox.state = 'pending'` rows and `needs_review` rows; never requeue an uncertain send without checking Twilio.
- Consent, phone numbers, and check-in answers are sensitive program data. Service-role routes and authorized cohort administrators are the access path; do not log message bodies or phone numbers.
