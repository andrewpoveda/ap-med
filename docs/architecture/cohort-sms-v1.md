# Cohort SMS V1 rollout checkpoint

## Status and boundaries

The repository contains the cohort-generic SMS data model, reusable cohort-application phone/consent fields, web meeting check-ins, a Twilio adapter, an inbound webhook, and a protected sender endpoint. Ascenso is the first public application flow using the shared fields; its broader application questions and public route remain Ascenso-specific. This work has not deployed those changes, applied any SMS migration to a hosted database, configured Twilio credentials, or enabled a cohort. It has not inspected those hosted settings. No SMS schedule has been added to `vercel.json`.

`SMS_FEATURE_ENABLED` is absent or false by default. Every `cohorts.sms_enabled` value defaults to false. Both switches must be on for new member dashboard SMS enrollment and the sender to operate. The cohort switch enables the shared web meeting check-in; a global sending pause leaves that web form and past answers available. A member with a stored SMS number can revoke consent or remove that number from the dashboard while sending is paused; a member without stored SMS data sees no SMS controls while it is off. The current web surveys, email digest, and meeting-log behavior remain separate and unchanged.

Phone collection at application time has its own cohort setting, `cohorts.config.sms_phone_collection`: `off`, `optional`, or `required`. Missing or invalid values mean `off`; no existing cohort is enabled by the migration. `required` requires a US phone number, never SMS consent. The text consent box stays separate and unchecked by default, and editing the phone clears a previous choice. Collection can be enabled while both sending switches remain off. The trusted cohort row determines what the public form shows and what the intake route accepts: `off` ignores even forged or stale phone/consent fields and stores no SMS answer keys. An insert-time database guard applies the current setting if an administrator changes it while an applicant submits. Ascenso must be explicitly set to `optional` before its application collects phone numbers under this policy.

## Data path

- Consent belongs to a person within a cohort. The shared intake validator normalizes the US number and records the exact disclosure, version, and server timestamp in `cohort_applications.answers` when collection is enabled. Approval copies a missing contact into `cohort_sms_contacts` without overwriting a later member preference, even if the collection setting changed after submission. If a person has two roles in one cohort and the second application conflicts with the saved phone or effective consent, the approval warns the administrator to ask the member to review SMS settings. Phone entry alone never authorizes a send.
- `meeting_checkins` is the one channel-neutral answer record for both the authenticated web form and SMS. Each row identifies the cohort, pair, booked session, and member. A check-in answer does not assert attendance or create a `meeting_logs` row. Existing mid-year/end-year `surveys` and `survey_responses` keep their current meaning.
- The sender only considers scheduled sessions 18–30 hours ahead for reminders and sessions 1–25 hours past for check-in prompts, including meetings marked no-show. These bounded windows prevent a new cohort enablement from backfilling old meetings. A unique outbox intent allows one reminder and one question per session/contact. A database claim and immediate eligibility recheck precede each provider call. Both checks prevent a reminder after its meeting moves outside the 18–30 hour window. Definite rejection and uncertain acceptance are retained; uncertain sends require manual review and are never automatically resent.
- A Twilio webhook verifies the signature, Account SID, Messaging Service SID, and fixed receiving number. Its inbound parser needs no outbound API key or enabled send switch, so STOP still works during a send outage. The database deduplicates `MessageSid` and records STOP/START/HELP before attempting reply matching. A check-in reply requires its unique 12-character code plus the exact From/To pair, an unexpired previously attempted prompt, and current member/meeting context. Replies to attempted prompts remain valid during an outbound pause, even when the provider result needs review. Pending, failed, and superseded prompts cannot take replies. A reply without a unique eligible match is not attributed; unmatched message bodies are not stored. STOP suppresses the phone across cohorts. START never renews AP MED consent, including when a previous STOP webhook was missed; the member must opt in again through the authenticated web flow.
- Dashboard opt-in takes a database phone lock and checks the suppression revision and the prior contact state before saving consent. A STOP/START or a later member revocation during that request makes it stale; the member must submit fresh consent. The STOP event timestamp is assigned after the same lock, so it cannot appear to precede a consent that it actually followed.

## Reusing collection for another cohort

In cohort settings, choose `optional` or `required phone` for a cohort whose public application is connected to AP MED. Its server-rendered application page should read the trusted cohort row, pass `getCohortSmsCollectionMode(cohort.config)` to the shared `CohortSmsContactFields`, and submit the standard `phone_number` and `sms_consent` keys when collection is on. Its intake route should re-read that cohort row and use `validateCohortSmsCollectionInput` plus `cohortSmsCollectionAnswers`; these handle validation, the off-mode omission, and server-created consent evidence. The existing cohort application approval route uses the shared `handoffApplicationSmsContact` helper for every cohort. No new phone column, consent table, or provider integration is needed for another cohort.

The only public application page and intake mapping currently implemented are Ascenso-specific. An institution with different questions still needs its overall application route and form connected; the shared SMS pieces should be reused there instead of copied.

## Setup before a test-number pilot

1. Review and apply the SMS migrations in filename order, from `supabase/migrations/20260926201229_sms_foundation.sql` through `supabase/migrations/20260927193855_sms_stop_consent_order_guard.sql`, before deploying dependent code. This includes the phone collection setting migration (`20260927192336`), the application insert guard (`20260927193648`), and the STOP/consent ordering guard (`20260927193855`). These migrations add a default-off cohort sending column, tables, triggers, and service-role RPCs; they do not enable sending or set a phone collection mode for any cohort. Arrange the normal backup and migration review. Do not replay the production baseline. No repository snapshot proves which migrations are already applied to a hosted database.
2. After deploying the application and verifying the configured Ascenso cohort, set its **phone collection** setting to `optional` in cohort settings before testing the public application. This does not enable SMS sending. Future cohorts use the same setting and shared contact fields/validator/approval handoff when their overall application flow is connected. A new institution's application questions and public route are still separate work; changing this setting alone does not create a public application for it.
3. Publish and review publicly accessible AP MED privacy and terms pages for the SMS use case; this repository currently has no such routes. Twilio's A2P campaign review asks for both URLs and a verifiable opt-in flow. The privacy policy must address mobile-number non-sharing for marketing, message frequency, and message/data rates. Keep the separate, unchecked onboarding checkbox/disclosure and timestamped consent evidence available as the flow proof. Create a Twilio Messaging Service with **one fixed two-way US sender** in its pool, configure Advanced Opt-Out, and complete the appropriate US A2P 10DLC Brand/Campaign approval before sending. Configure the inbound **POST webhook on the Messaging Service**, not only the sender number, so signed requests include its Service SID. Use the canonical AP MED hostname for the webhook even if Ascenso has its own public site.
4. Configure server-only `TWILIO_ACCOUNT_SID`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET`, `TWILIO_AUTH_TOKEN`, `TWILIO_MESSAGING_SERVICE_SID`, `TWILIO_FROM_PHONE_E164`, and `TWILIO_INBOUND_WEBHOOK_URL`. Set the last variable to the exact public `https://.../api/webhooks/twilio/sms` URL **without** a fragment. The auth token verifies inbound signatures; the API key sends outbound messages. Never expose these through `NEXT_PUBLIC_` variables.
5. In Twilio, configure the same inbound URL as a POST webhook **with** the connection override `#rc=2&rp=ct,rt,5xx`. Twilio's default retry policy covers connection failures only: an app 503 after a transient database failure will **not** be retried without `rp=5xx`. Twilio excludes the fragment from signature calculation, so keep it out of `TWILIO_INBOUND_WEBHOOK_URL`. Verify that a signed webhook receiving a test 503 is retried and that duplicate delivery is deduplicated before sending pilot messages. Monitor webhook failures; the short retry window cannot recover a prolonged outage.
6. Keep the existing `CRON_SECRET` for `/api/cron/sms`. The route is implemented but deliberately absent from `vercel.json`: the current repository has only a daily 13:00 UTC email digest, and the hosted plan is unverified. The 12-hour reminder window requires a scheduler more often than every 12 hours; hourly gives headroom for jitter and an occasional missed run. Check the actual hosting plan and schedule support before registering a cron or promising reminder timing.
7. In a nonproduction environment, test real-number delivery and inbound messages, duplicate and late webhooks, STOP, START followed by fresh web consent, phone changes, canceled meetings, overlapping cohorts, web answers before SMS replies, provider timeouts, and stale sending reconciliation. Inspect `needs_review` rows against Twilio before resolving them. Only then request authorization to enable the Ascenso cohort in production.

## Known limits

- No handset ownership check is performed. Shared, mistyped, or reassigned numbers may receive a short prompt; keep detailed program information in the authenticated web dashboard.
- Changing phone collection from `off` to `required` while an applicant has an older form open can make that form stale. The server applies the current setting; the applicant must reload to see the newly required field.
- Provider acceptance is not handset delivery. V1 does not consume Twilio delivery-status callbacks; review provider message logs when investigating a missing text or a `needs_review` attempt.
- A STOP can race with an already claimed provider call. The sender rechecks eligibility immediately before calling Twilio, and Twilio Advanced Opt-Out is the final backstop; an external send cannot be atomic with a database update. If both STOP and a later START webhook are lost during an outage, reconcile Twilio opt-out history before resuming sends.
- The sender uses bounded per-run limits. If the pilot exceeds those limits or a scheduler is down beyond the due window, SMS may be skipped rather than sent late. The web check-in remains available while `cohorts.sms_enabled` stays on, even if global sending is paused. Turning off that cohort flag also pauses new web check-ins; authorized administrators can still read prior answers. Operators should inspect stale `sms_outbox.state = 'pending'` rows and `needs_review` rows; never requeue an uncertain send without checking Twilio.
- Do not close a cohort while expecting replies to an outstanding seven-day check-in prompt, because closed cohorts reject new answers.
- Consent, phone numbers, and check-in answers are sensitive program data. Service-role routes and authorized cohort administrators are the access path; do not log message bodies or phone numbers.
